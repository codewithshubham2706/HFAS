# LLM Insights Agent — orchestration & prompts

Pattern: **aggregated inputs only**. The agent never receives raw events,
session replays, or PII. It receives: score distributions, leak-path tables,
error-code counts, cohort deltas. Validation SQL it proposes is executed by a
human-approved runner (never auto-executed against production).

```
┌─────────────┐   nightly     ┌──────────────────┐   aggregated   ┌─────────────┐
│ warehouse    │ ───────────▶ │ context builder  │ ─────────────▶ │ LLM agent   │
│ (Postgres)   │              │ (SQL views only) │                │ (no PII)    │
└─────────────┘               └──────────────────┘                └──────┬──────┘
        ▲                                                                │
        │        hypotheses[].validation_sql reviewed & run by analyst    │
        └────────────────────────────────────────────────────────────────┘
```

## Context builder (exact SQL fed to the model)

```sql
-- context_weekly.json (generated by scripts/build_llm_context.sh)
SELECT
  (SELECT jsonb_build_object(
     'sessions_7d', count(*),
     'median_experience', percentile_cont(0.5) WITHIN GROUP (ORDER BY experience_score),
     'median_effort',     percentile_cont(0.5) WITHIN GROUP (ORDER BY effort_score),
     'median_intent',     percentile_cont(0.5) WITHIN GROUP (ORDER BY intent_score))
   FROM session_metrics WHERE session_date > current_date - 7) AS health,
  (SELECT jsonb_agg(jsonb_build_object(
     'from_step', from_step, 'to_step', to_step,
     'exit_rate_pct', exit_rate_pct, 'sessions', sessions_entering))
   FROM (SELECT * FROM top_leak_paths ORDER BY exit_rate_pct DESC LIMIT 10) t) AS top_leaks,
  (SELECT jsonb_agg(jsonb_build_object('error_code', upload_error_codes, 'sessions', n))
   FROM (SELECT upload_error_codes, count(*) AS n
         FROM high_intent_high_friction
         WHERE upload_error_codes IS NOT NULL
         GROUP BY upload_error_codes ORDER BY n DESC LIMIT 8) e) AS error_mix,
  (SELECT jsonb_agg(jsonb_build_object(
     'scenario', scenario, 'outcome', outcome, 'p95_ms', p95_ms))
   FROM synthetic_status_daily) AS synthetic_health;
```

## Prompt 1 — weekly root-cause analysis

```
SYSTEM:
You are the product-intelligence analyst for HFAS, a healthcare financial
assistance platform. You receive ONLY aggregated, de-identified metrics —
session counts, score distributions, error codes, funnel exit rates. If any
input appears to contain personal data, refuse and say "context violation".

Respond with STRICT JSON matching the schema after the context. Be specific;
cite the numbers you used. Rank hypotheses by expected impact × confidence.
Max 5 hypotheses.

USER (context):
{context_weekly.json}

Respond with JSON:
{
  "generated_at": "<iso>",
  "health_summary": "<2 sentences citing numbers>",
  "hypotheses": [
    {
      "rank": 1,
      "hypothesis": "<one sentence: what is breaking and for whom>",
      "evidence": ["<metric>: <value> vs <baseline>"],
      "confidence": 0.0-1.0,
      "expected_impact": "<e.g. +X% submit rate if fixed>",
      "validation_sql": "<single read-only SELECT validating this on the warehouse>",
      "remediation": ["<concrete step>", "…"],
      "owner_team": "web | api | ocr | ops"
    }
  ]
}
```

## Guardrails (mandatory)
- No PII, no raw event payloads, no replay content in prompts — context builder output is the ONLY allowed input.
- `validation_sql` is executed read-only, row-capped (LIMIT 1000), by an analyst — never auto-run.
- All agent output lands in a human-reviewed queue; nothing auto-ships.
- Log the agent's own cost/token usage per run (ops KPI).
